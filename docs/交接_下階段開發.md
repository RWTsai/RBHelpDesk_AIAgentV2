## 5a. Agent 迴圈走 Responses API

**已完成遷移。** 起因是測試環境把 `OPENAI_MODEL_CHAT` 設成 `gpt-6-astra` 後每一題都失敗，追下去發現官方 function-calling 指南已寫明 **GPT-6 Astra 與 GPT-6.1 Sol 的 tool calling 只支援 Responses API**，而後續新模型預期也不會再支援 Chat Completions 的 function tools。所以這是必走方向，不是權宜。

遷移前實測 `gpt-6-astra` 在 `/v1/chat/completions` 的行為（帶工具時無解，API 建議還自相矛盾）：

| | `effort=low` | `effort=none` | 省略 |
|---|---|---|---|
| 不帶工具 | 可用 | 不支援 none | 可用 |
| **帶工具** | **400** | **400** | **400** |

### 改了什麼

| 項目 | 內容 |
|---|---|
| 工具宣告 | `agents/tools.py:to_responses_tools()` —— 扁平的 `{type, name, description, parameters}`，不包在 `function` 裡 |
| 呼叫 | `agent_node._respond()` → `client.responses.create(model, instructions, input, tools, tool_choice)`；系統提示走 `instructions` |
| 回應解析 | 從 `res.output` 取 `type == "function_call"` 的項目（欄位 `call_id`／`name`／`arguments`）；最終文字用 `res.output_text` |
| 工具結果 | 追加 `{"type": "function_call_output", "call_id", "output"}` 回 `input` |
| 對話接續 | **每一輪把模型自己的 `res.output` 原封不動接回 `input`**（含 `reasoning` 項目）。少了它們，下一輪的 `function_call_output` 會對不上 `function_call` 而 400 |
| 推理強度 | 兩個 API 形狀不同（`reasoning_effort="low"` 對 `reasoning={"effort": "low"}`）。`_call_model()` 依 `effort → 省略 → none` 退讓，並按 **(API, 模型, 有沒有帶工具)** 快取，避免每次呼叫先失敗一輪 |
| 留存 | 新增 `OPENAI_STORE_RESPONSES`（**預設 off**）。Responses 預設會把對話留在 OpenAI 端供事後取回，而這裡送的是內部知識庫與資料庫結果 |

**沒有改**：快速路徑（`_fast_path`）與驗證器（`_verify`，用 `.parse()` 結構化輸出）都不需要工具，仍走 Chat Completions。所以 `_chat()` 保留。

## 7. db-pmm 領域知識（本次最大產出）

細節都在 `skills/db-pmm/SKILL.md`（556→729 行），**每一條都在 RBMS 上驗證過，文內 14 段 SQL 全部可執行**。下階段要改這個 Skill 前，先讀以下清單避免改錯：

**業務規格與實際資料庫不符的五處（以資料庫為準）**

1. 沒有 `ProductionID` 欄位，實際是 `ProductionLineID` → `BIProductionLine`。
2. 交易表接的是 **`BreedAliasID`** 不是 `BreedID`；路徑 `BIBreed.ID → BIBreedAlias.BreedID`、`BIBreedAlias.ID → 交易表.BreedAliasID`。
3. 規格代號四位零補齊：業務文件寫的 `084` 實際是 **`0084`**（庫存 221 萬、第二大）。
4. 「生產階段」不只看 `SpecID`，階段路徑在 `BIProcess`（`Name`＝`翻種0075->0105`、`SpecBegin`／`SpecEnd` 存 `BISpec.ID`、`WorkDay`＝預計天數）。
5. 分組未涵蓋全部規格（`0050`／`0060` 在小苗與中苗之間，`0114` 以上超過大苗）。

**業務規則（業務單位確認）**

- **「台灣」只算彰化生產部（1）**；台灣契作產線（5）與種原課（9）不列入，但回答**必須提醒並附數量**（兩者合計 110 萬 > 彰化 73 萬）。
- **切花苗株栽培階段，生管依花色需求把不同品種歸成同一批次** → 批號含多品種是設計使然。
- **良率分母預設進貨（R08）**，但查詢前要問是從進貨或特定階段起算。
- **瓶株換算取整數**；「種多久」要先問起算點，迄點預設為詢問當下。

**光看欄位推不出來的陷阱**

- `BIReason.TransferType` 1／2／3 分別是苗株／切花／盆花，同名原因會重複列，JOIN 只能用 `ID`。
- `BatchNo` **不唯一**（105,736 列只有 32,292 個批號），且與 `BatchNoSrc` **定序不同**（`SQL_Latin1_General_CP1_CS_AS` vs `Chinese_Taiwan_Stroke_CI_AS`）→ 直接 JOIN 會報定序衝突；`BatchNo` 區分大小寫，比對一律加 `COLLATE`。
- **日期沒有 NULL，空值是 `0001-01-01`** → `IS NULL` 永遠不命中，要寫 `> '1900-01-01'`。
- **`CompletedDate` 可能是未來日期**（5,625 列）＝尚未完工的預計完工日，算天數要包 `CASE ... THEN GETDATE()`。
- 組培（瓶）與種苗（株）**單位不同不可相加**。
- **負數移轉不等於損耗**：跨組移轉苗株 −4,519,204／盆花 +4,519,324 互為鏡像，是 YP→PP 交接。
- 切花訂單按**花色**下單（`CFOrderDetail` 無 `BreedAliasID`），數量欄位拼成 **`FixedQuqntity`／`NormalQuqntity`**，`GradeIDList` 等是逗號分隔字串不能 JOIN。

**對帳基準**：`SUM(YPTransferRecord.Quantity)` = `SUM(View_苗株庫存數量.TotalQuantity)` = 6,482,770（完全相等）。改動庫存相關查詢後用這條驗。

### 10.5 新模型的參數（兩邊都踩過）

新一代模型（gpt-5.x／gpt-6 系列）不收 `max_tokens`、也不接受非預設的 `temperature`，
各自都會讓請求整個被拒（400）。

- `max_completion_tokens` 舊模型也吃，所以不用依模型分流
- `temperature` 直接不送（預設 1）
- **上限要調高**：`max_completion_tokens` 把推理 token 也算進去。沿用原本的字數上限
  很可能被推理吃光，`content` 回空字串，然後在 JSON 解析處炸掉——症狀看起來跟真正
  的原因毫無關係，比 400 難查得多

已處理：`.NET` 的 `OpenAIService` ×1、`TripleExtractService` ×3；Python 的
`ingest_docs._vision_text`（原本 `temperature=0`，而 `_vision_enrich` 是逐頁 except，
400 會被吃掉變成「整份文件的圖片內容無聲消失、狀態還是 Done」）。

### 10.8 Agent 迴圈與執行緒

迴圈的停止條件有四個：`AGENT_MAX_STEPS=4`、`AGENT_TIME_BUDGET_SEC=40`、
`AGENT_MAX_VERIFY_RETRY=1`、模型自己不再叫工具。時間預算用 `over_budget()`
在迴圈各處重新評估，不是在頂端算一次。

執行緒有四處：`heartbeat`（app.py:173）、`doc_graph_client.warmup`（:182）、
**每一筆 LINE event 一個**（:147，webhook 立刻回 200）、工具並行
（`agent_node.py:425`，≤4）。再加上 Flask `app.run()` 預設 `threaded=True`。

`doc_graph_client.is_ready()` 就是為了 warmup 執行緒和請求執行緒賽跑而存在：
沒有它，載入期間進來的請求會**安靜地卡在 `_LOCK` 上**等 15～57 秒走完，整題超過
LINE 的 reply 視窗。檢查刻意放在 `start_loading` 之前，也刻意不拿鎖。

**進行中的進度只有兩個地方看得到**：LINE 端的 loading 動畫與超過 8 秒的推播通知；
Python console 的工具層 log。`IT_KB_AgentTrace` 是整題跑完才一次寫入，查詢中是空的。
agent 層沒有逐輪的 log（看不到「現在第幾輪、這輪決定叫哪些工具」）——這是空缺。
